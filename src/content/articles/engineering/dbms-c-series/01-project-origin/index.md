如果只看最终目录，DBMS_C 像是从一开始就有一张完整蓝图：File、Buffer、Transaction、Record、Metadata、Parser、Plan 和 Query 一层压着一层。但 Git 历史留下的过程并没有这么整齐。

最早的提交发生在 2024 年 10 月 31 日。提交说明是“在 map 成功使用版本”，一次性加入了一万多行代码。紧接着的提交写着“Schema 完成还未进行测试”，几个小时后才出现“Layout 完成测试版本”。后面的记录同样直接：BufferList 编写测试、ConcurrencyManager 编写测试、Rollback 还存在问题、doRecovery 测试没问题。

这些说明更接近我当时的真实状态：我不是先设计出一套成熟数据库架构，再按图施工；而是带着数据库原理课里的概念，一层一层把它们变成能够互相调用的 C 代码。

## 为什么要自己写一个数据库

学完数据库原理后，我知道事务需要原子性，知道 Buffer Pool 用来减少磁盘 I/O，也知道查询优化器会选择执行计划。但如果继续追问，很多理解就停在图和定义上：

- 一条记录在页面中究竟是什么布局？
- Buffer Pool 返回的到底是一份页面副本，还是共享页框？
- `ROLLBACK` 从哪里找到修改前的值？
- `SELECT` 的投影和过滤是在什么时候执行的？
- 元数据本身保存在哪里？

只做课程练习很难同时碰到这些问题。它们之间存在约束：事务依赖缓冲池，缓冲池又必须配合日志；记录页依赖事务接口；计划执行必须通过记录层才能接触数据。只有把链路接起来，我才能知道自己是否真的理解了这些概念。

所以这个项目最初的目标不是“做一个能取代现有数据库的产品”，而是实现一个足够小、又能覆盖主链路的关系数据库原型。最后形成的入口仍然很简单：一个本地命令行、一个固定的数据库目录和一组有限 SQL。

```c
#define BLOCK_SIZE 4096
#define BUFFER_SIZE 8
#define LOG_FILE "SimpleDB.log"

SimpleDB *db = SimpleDBInit(
    "Show2",
    SIMPLE_DB_INIT_VAL,
    SIMPLE_DB_INIT_VAL
);
```

这里没有配置中心，也没有服务进程。块大小、缓冲帧数量、日志文件名和默认数据库目录都直接写在程序里。这种设计不灵活，但把实验规模限制住了，让我能够先观察页面、事务和 SQL 执行的关系。

## 为什么没有直接读 MySQL 或 PostgreSQL

成熟数据库当然更值得学习，但它们并不适合作为我当时的第一份内核实践。

真正的数据库不仅有存储和查询，还要面对多进程或多线程、网络协议、权限、复制、监控、不同平台和多年兼容性。刚学完数据库课程时直接进入这种代码库，我很容易只记住函数名称，却不知道一条最基本的查询为什么需要这些抽象。

DBMS_C 选择的是一个中间尺度。它比“在数组上执行 SELECT”的课堂作业更完整，又比工业数据库小得多。我可以在一次调试中从 Parser 跟到 Page，也可以直接打印日志 boundary 或页框 pin 计数。系统越小，某个设计错误产生的后果越容易被看见。

这种选择当然有代价。我实现的是教学模型，不是 MySQL 或 PostgreSQL 的缩小版本。项目中的块级锁、定长记录、嵌套循环乘积和 undo 日志，只能帮助我理解核心机制，不能代表成熟数据库的真实复杂度。

## 为什么选择 C

如果目标只是尽快得到一套可用 SQL 接口，C 并不是最省事的选择。字符串、容器、错误处理和内存释放都需要自己处理。DBMS_C 的 `Lib/` 最终包含 CString、ByteBuffer、链表、向量、Map、Trie 和红黑树，其中不少工作与 SQL 本身无关。

但正因为如此，C 迫使我面对数据库内核无法回避的边界。

`Page` 不是一个抽象概念，而是一段带 position 的字节缓冲区；`Layout` 不是表结构的另一种名字，而是字段名到字节偏移的映射；一个 `Buffer *` 是共享页框还是一份值拷贝，会直接影响事务修改能否被其他模块看见。

例如整数读取最后会落到类似这样的代码：

```c
int PageGetInt(Page *page, int position) {
    int output;
    bufferGetIntPosition(page->buffer, position, &output);
    return output;
}
```

再往上一层，记录字段的位置由槽号和 Layout 共同决定：

```c
int fieldPos = slot * layout->SlotSize
             + LayoutOffset(layout, fieldName);
```

这两段代码把“读取某条记录的某个整数字段”还原成了一个很具体的动作：找到块，固定页框，计算槽起点和字段偏移，再从四个字节中取出整数。对我来说，这正是选择 C 的意义。

它也让我为内存问题付出了足够多的调试成本。当前项目仍有不少 CString 临时对象没有释放，部分 API 的所有权没有统一，错误路径也经常直接返回或退出。这些不足不是 C 的优点，却是这次实践留下的重要教训：底层控制能力和生命周期责任是同时出现的。

## 最初怎样切分项目

我最初需要的不是完整 SQL，而是一条可以逐层搭建的依赖链。

第一层是基础容器和字节缓冲。没有字符串、Map 和动态数组，后续模块连基本的数据结构都难以表达。

第二层是 File、Page 和 Log。`BlockID` 用文件名和块号定位数据，FileManager 负责固定大小块的读写，Page 把原始字节包装成整数和字符串接口。日志也复用相同的页面机制。

第三层是 Buffer 和 Transaction。缓冲池负责让页面留在内存里，事务在页级读写周围增加锁和 undo 日志。只有这层稳定后，RecordPage 才能放心地把字段值交给事务接口。

第四层是 Record 和 Metadata。Schema、Layout、RID、RecordPage、TableScan 组成记录存储；系统目录再使用同一套 TableScan 保存表和字段定义。

最后才是 Parser、Plan 和 Query。SQL 被解析成结构化对象，Planner 组织计划树，Plan 打开后变成 Scan 链，Scan 再向下读取记录。

这个顺序后来体现在最终目录里，但提交历史说明实际开发并不是严格的瀑布流程。Schema、BufferList、并发管理和 RecoveryManager 在很短时间内交叉出现，许多接口是一边写上层一边回头修下层。

## 第一次阶段：让主链路跑起来

2024 年 10 月到 12 月是原型快速成形的阶段。

10 月底的提交集中在 Map、Schema、Layout 和 BufferList。11 月初开始加入锁、事务号、错误类型和 CMake 调整。11 月中旬的重点转向 LogRecord、Transaction 和 RecoveryManager，提交说明连续记录了回滚调试。11 月下旬到 12 月，Record、Metadata、Parser、Query 和 Plan 逐渐合并成能够运行的整体。

12 月 22 日出现两次“最终版本 DBMS_C”提交。这里的“最终”更接近毕业设计阶段的功能收束：主要模块已经存在，基本 SQL 可以演示，但工程结构、测试和发布仍然有很多问题。

这一阶段最重要的成果不是某个单独算法，而是终于把依赖链连通了：

```text
SQL
  → Parser
  → Plan
  → Scan
  → RecordPage
  → Transaction
  → Buffer
  → File
```

当这条链路第一次工作时，我才真正意识到数据库原理中的模块不是平行章节。页面布局改变会影响日志旧值的位置；Buffer 生命周期错误会让 rollback 读到另一份状态；Planner 生成了 Scan，也仍然需要事务层保证下面的读写语义。

## 第二次阶段：把课程代码整理成工程

2025 年 6 月和 8 月，项目经历了一次明显的模块化整理。提交历史中先出现一次新的源码导入，随后按 buffer、transaction、parser、planner、query、index、record 和 DBMS 入口拆成一组独立提交，并加入 GitHub Actions 和 CMocka 测试入口。

这种整理改善了目录边界，但也留下了一些“看上去有模块，实际上只完成了结构”的部分。哈希索引代码存在，查询计划却没有使用它；死锁检测器存在，并发管理器却没有接入；`OptimizedProductPlan.c` 甚至还是空文件。

这让我逐渐区分三种状态：

1. 文件和结构体已经创建；
2. 模块内部函数可以单独运行；
3. 模块真正进入主流程，并被端到端测试覆盖。

只有第三种才能算用户实际拥有的能力。这个标准后来也成为我重新写项目 README 和本系列文章时最重要的约束。

## 第三次阶段：重新理解并公开它

2026 年我又回到这个项目。3 月加入了 BetterQueryPlanner 的实验代码，尝试按记录数和连接代价选择连接顺序；5 月增加命令级 Trace 和一套分章节教程；9 月则集中处理 v1.0 归档。

Trace 对我很重要，因为它把原来只能在调试器里观察的对象关系变成了命令行输出：

```text
QueryData
  ProjectPlan
    SelectPlan
      TablePlan
  ProjectScan
    SelectScan
      TableScan
```

但真正耗时的并不只是新增功能。v1.0 整理时发现，CMake 引用的一些 CList、错误模块、测试和 demo 文件没有被 Git 跟踪；仓库里反而跟踪了运行生成的数据库文件；文件名中存在多余空格，测试文件名也有拼写错误；一次批量处理还破坏了大量中文注释。

这些问题说明“在我的电脑上可以继续开发”和“别人全新 clone 后可以复现”是两个标准。最终归档提交补回缺失源码、移除构建与数据库产物、恢复注释、整理文档，并在干净副本上重新执行构建和测试。

## 几个真正改变设计的问题

### Buffer 被复制后，修改消失了

2024 年 11 月 13 日的一条提交直接记录：“BufferList 中得到的东西进行修改后 BufferManager 中不能看到。”

当时 BufferList 的 Map 保存的是 `Buffer` 值。把页框放进 Map 时，结构体被复制；事务之后修改的是 Map 中的副本，而 BufferManager 仍然持有原来的对象。后续修复把映射值改成保存 `Buffer *` 的包装结构，让两边共享同一个页框。

这个 bug 让我第一次清楚地看到，“按值还是按指针”不是代码风格问题，而是存储系统的一致性问题。

### 每个 Buffer 都创建自己的管理器

早期的 `BufferInit` 会重新调用 `FileManagerInit` 和 `LogManagerInit`。这样做表面上减少了外部依赖，实际上破坏了共享状态：页框使用的日志管理器和事务看到的不是同一个实例，文件句柄与最新 LSN 也可能分离。

11 月 14 日的修复只有两行，把重新初始化改成直接保存传入指针：

```c
buffer->fileManager = fileManager;
buffer->logManager = logManager;
```

代码改动很小，修正的却是系统对象之间的所有权关系。

### Rollback 不是把新值改回去那么简单

提交历史先明确写下“Rollback 还存在一定问题”，随后才逐步修正日志迭代条件、事务号读取、字符串记录长度、字段偏移和日志类型。SETSTRING 日志一度被写成 SETINT，文件写入后也需要显式刷新才能稳定观察到回滚结果。

最后真正起作用的不是某个额外的 if，而是重新校准整条路径：修改前记录旧值，日志能够逆序遍历，LogRecord 可以准确还原块和偏移，undo 写回时禁止生成新的普通更新日志。

## 回头看最初的规划

DBMS_C 最初想覆盖存储、事务和 SQL 主链路，这个目标基本完成了。但开发过程也证明，模块名称覆盖完整，不代表每个模块都达到同样的成熟度。

项目当前最可靠的是单机命令行下的页式存储、记录扫描、基础 SQL 计划和显式回滚。最不完整的是自动崩溃恢复、真实并发、索引接入和查询优化。它仍然适合作为数据库内核学习记录，却不应该被描述成工业数据库。

如果重新开始，我可能会更早写下每个模块的所有权规则和可验证目标：BufferList 是否保存页框身份，日志 API 是否只接受旧值，锁冲突怎样返回错误，恢复测试怎样模拟进程异常退出。这些问题看起来没有 SQL 功能直观，却决定了后面的实现是否可信。

我没有通过这个项目一步成为数据库专家。更准确地说，DBMS_C 让我第一次知道自己原来不懂哪些细节，也让我能够把“页、日志、事务、计划”这些课本词汇还原成真实的指针、偏移、文件写入和失败测试。
